# 磁盘卫生规范

> 本文是 [`DISK_HYGIENE.md`](./DISK_HYGIENE.md) 的简体中文译本。规则编号与英文版
> 严格一一对应；两者冲突时以英文版为准。

**构建产物的存活时间，不得长于产生它的工作区；worktree 的存活时间，不得长于产生它的任务。**

生成物应当紧挨着产生它的东西。worktree 与构建缓存都放在所属仓库内部，这样删除仓库
就等于删除了它产生的一切——既不会有孤儿目录，也不需要去第二个地方找。

本规范适用于机器上的每一个仓库，以及在其中工作的每一个主体——无论是人还是自动化程序。

---

## 1. 布局

**L1 — worktree 放在仓库内部。**
worktree 必须创建在 `<repo>/.worktree/<name>`。仓库旁边不放置任何东西，也不存在
机器级的全局 worktree 根目录。该目录由 Git 忽略，因此永不表现为改动。

> **已知的代价。** 由于 `.worktree/` 被忽略，在仓库内执行 `git clean -x` 会一次性删掉
> 所有活跃 worktree，以及那些在任何其他地方都不存在的未提交成果。因此该命令被彻底禁止
> ——见 L6。这既是内聚的代价，也是它的对立面——全局根目录——的解法：那个目录没人记得去看。

**L2 — 一个仓库只有一个 clone。**
每个仓库只保留一个规范 clone。变体是 worktree，不是额外的 clone。若存在第二个顶层
目录、其 `.git` 指向该规范 clone，则必须迁入仓库内或删除。

**L3 — 禁止嵌套。**
worktree 内不得再包含 worktree。`.worktree/<name>/.worktree/` 属于违规，不是更深一层
的组织方式。

**L4 — 命名。**
`<repo>-<branch-slug>-<YYYYMMDD>`，小写、连字符分隔、不超过 60 字符。工具内部的标识
（会话 id、哈希值）只能作为名称的一部分，不得作为上级目录名。

**L5 — 忽略项属于布局的一部分。**
承载 worktree 的仓库，其 `.gitignore` 必须同时包含两个路径：

```
/.worktree/
/build-cache/
```

开头的斜杠把两条模式锚定在仓库根目录，**不可省略**。省略后 `.gitignore` 会匹配任意
层级的同名目录，于是某个 worktree 在自身内部跑一次构建，就会悄悄长出第二个
`build-cache/`——Git 看不见、台账里没有、B2 也管不到它。

这两条要提交进版本库，而不是本地排除：只存在于某个开发者 `.git/info/exclude` 里的
忽略规则，会被其他人原样提交上去。

**L6 — `git clean -x` 与 `git clean -X` 全局禁止，任何形式都不允许。**
这两个参数都会删除被忽略的路径，而 `.worktree/` 与 `build-cache/` 正是被忽略的。于是
那条看起来只是「清掉构建产物」的命令，会连带删掉仓库内所有活跃 worktree——包括在任何
其他地方都不存在的未提交成果，以及 worktree 自身的 Git 元数据。且不可恢复。

禁止的形式包括 `-x`、`-X`，以及任何携带其中之一的组合：`-xdf`、`-fdX`、
`--force --ignored`，还有会展开成它们的 shell 别名。用 `-e` 收窄范围不能作为替代方案：
它只保护到「有人记得列出来」的那些路径，而且必须由每个工具、每一次都写对。一条依赖
「记得写例外」的规则，不是规则。

| 目的 | 应使用 |
|---|---|
| 删除未跟踪且未被忽略的文件 | `git clean -fd` |
| 先看会删什么 | `git clean -nd` |
| 清空构建产物 | 直接删除槽位——`build-cache/<name>/` 或 `build-cache/main/` |
| 移除单个 worktree | `git worktree remove <path>` |
| 清理失效的 Git 元数据 | `git worktree prune` |

`git clean` 不靠近提交环节：没有 hook 会被触发，任何扫描也无法查出它已经毁掉了什么。
唯一的硬拦截是 shell 包装器拒绝这两个参数。在未安装该包装器的地方，本条属于纪律——
凡是改动涉及清理脚本的变更，都应按纪律条款来审查。

**L7 — 声明过的路径必须从所有索引器中排除。**
`.worktree/` 里是每个活跃 worktree 的完整检出，`build-cache/` 里是对应的构建树。
两者都必须从编辑器的文件搜索与系统索引中排除。若不排除，一次搜索会返回同一份文件
五十次，系统索引也会按磁盘已有内容的体量继续膨胀。

## 2. 生命周期

**T1 — 并发上限：每仓库 50 个。**
单个仓库已注册的 worktree 不得超过 50 个。创建第 51 个前必须先移除一个。上限统计的是
已注册的 worktree，不是目录数量。

**T2 — 合并即关闭。**
分支合入主线后 24 小时内必须移除对应 worktree。移除是「完成本次改动」的一部分，不是
另一件单独的清理任务。

移除是两半：`git worktree remove <path>`，**以及**删除配套的 `build-cache/<name>/`。
worktree 已经没了、缓存还留着，那就是一个任何扫描都无法归属的孤儿。

**T3 — 闲置过期。**
连续 7 天既无新提交、也无未提交改动 → 判为陈旧，移除。若存在未提交改动 → 判为阻塞，
只报告，不得单方面删除。**阻塞是延后，不是豁免**：拖到 T4 的 30 天上限时，仍然要先导出
再移除。

**T4 — 绝对上限。**
任何 worktree 无论处于何种状态，存在时间不得超过 30 天。超过后必须先将其工作成果推送
到分支或导出为 patch，再移除。

**T5 — 会话退出即清理。**
由自动化会话创建的 worktree，必须在该会话结束前移除；除非会话显式交接，即点名该
worktree 并说明下一步动作。

> **为什么 50 必须依赖 T3 与 T4 真正执行。** 50 是工作集额度，不是存储预算：按 B5 的
> 10 GB 上限计算，理论最坏情况是 500 GB。因此仅靠数量限制保护不了磁盘，真正起作用的是
> 时间限制。若 T3、T4 没有落地，T1 就会被撞到，然后失去意义。

## 3. 构建产物

**B1 — 在仓库内，产物只能出现在声明过的位置。**
仓库内允许存放生成物的路径只有两个：

| 路径 | 内容 |
|---|---|
| `<repo>/.worktree/` | worktree 本身 |
| `<repo>/build-cache/` | 全部构建与测试产物 |

产物出现在仓库内的其他任何地方——源码根、`Sources/`、worktree 根、包清单旁散落的
`.build`——均属违规。本条并不禁止产物存在，禁止的是它**未经声明**地存在。

按其性质本就位于仓库之外的产物——发布构建、可分发二进制——由 C3 管辖，且不得作为
普通构建的副产品出现。

**B1.1 — 验收标准就是 `git status`。**
在产物齐全的状态下——刚构建完或刚跑完测试——`git status --porcelain` 的输出中不得出现
任何生成物路径。放置正确的产物对 Git 是不可见的，因为两个声明位置都被忽略；凡是在输出
里出现的生成物，按定义就落在声明位置之外。

这条检查关心的是**出现了哪些路径**，不是工作区是否干净。带着普通未提交改动的工作区是
正常状态，说明不了任何问题——若要求输出为空，每个健康仓库都会失败。

**B2 — 唯一的缓存根，按 worktree 名镜像。**
`<repo>/build-cache/<name>/` 与 `<repo>/.worktree/<name>/` 一一对应。有两个保留槽位
不对应任何 worktree：`main/` 属于主检出，`shared/` 存放 B3 中所有 worktree 共享的依赖。
工具的原生目录名可以保留在槽位内部（`build-cache/<name>/.build/`、
`build-cache/<name>/DerivedData/`），但每个仓库用于审计、配额和删除的入口只有一个。

这种镜像不会自动发生，没有任何工具的默认行为会落到正确位置。每一条写产物的命令都必须
被显式指向自己的槽位——通过工具自带的参数（`--scratch-path`、`-derivedDataPath`、
`CARGO_TARGET_DIR`、`--virtual-store-dir`），或通过一个统一的
`WORKTREE_BUILD_CACHE` 变量，由创建 worktree 的那一方导出。**这段接线是必须真正去做的
部分**，本规范其余条款都建立在它已存在的前提上。

**B3 — 共享读，隔离写。**
已解析的依赖——包检出、语言包 store、下载的工具链——应当在同一仓库的所有 worktree 之间
共享，因为它们内容完全相同，重复下载既费时又费空间。共享内容放在 `build-cache/shared/`。
编译中间产物与链接输出必须按 worktree 隔离，因为并发写同一个构建目录会互相破坏。

| 类型 | 范围 | 原因 |
|---|---|---|
| 包 store、已解析依赖 | 共享 | 内容相同、体积大、获取慢 |
| 目标文件、模块缓存、链接产物 | 按 worktree 隔离 | 并发写入会冲突 |

**B4 — 天生可丢弃。**
`<repo>/build-cache/` 下的任何内容可以在任何时候无预警删除，代码不得将其当作输入读取。
不可删除的缓存不是缓存。

**B5 — 单 worktree 上限 10 GB。**
超出意味着反复全量构建，而非项目本身庞大，应作为问题项报告。

## 4. 缓存与产物

**C1 — 机器级缓存要有天花板。**
无法放进仓库的缓存——工具缓存、包管理器 store、家目录下的编译器缓存——各自应当不超过
10 GB。工具自带 prune 命令时优先使用它；整目录删除只适用于没有选择性回收手段的缓存。
把共享的包 store 整个删掉，会迫使所有 worktree 重新拉取，那正是 B3 想避免的成本。

**C2 — 设备与模拟器镜像可抛弃。**
设备文件系统快照与模拟器镜像中，不得存放未同时存在于仓库或产物库中的数据。30 天未使用
的模拟器删除；每个运行时最多保留 2 个。

**C3 — 发布产物只留 3 份。**
当前版本加上前两个版本。更早的构建移至外部存储或删除。

## 5. 配额与闸门

**Q1 — 可用空间阈值。**
可用空间高于卷容量的 15% 为正常；10%–15% 为告警；**低于 10% 即冻结**——在回升至 12%
以上之前，禁止新建 worktree、新增缓存条目、新增发布产物。冻结点与解冻点之间的间隔是
刻意设置的滞回：若共用一个阈值，每当构建或回收把数字推过它，状态就会反复翻转。

**Q2 — 总量上限。**
单个仓库的 `<repo>/build-cache/` 应当控制在卷容量的 10% 以内。B5 的 10 GB 是单个
worktree 的天花板，不是配额分配：平均体积由 T3、T4 控制。

触到上限时，先回收再新建。按 B4，删除某个闲置 worktree 的槽位始终是允许的；
相比之下，拒绝一次真正的构建需求是更糟的结果。

**Q3 — 在入口拦截，而非事后清理。**
新建 worktree、新增缓存条目或产物之前，必须先通过 T1、Q1、Q2 的检查。违规在创建时即被
拒绝，而不是事后报告。本规范中每一条规则，在入口拦截都比事后收拾更便宜。

## 6. 执行机制

| 时机 | 机制 | 覆盖规则 |
|---|---|---|
| 任意命令 | shell 包装器拒绝携带 `-x` 或 `-X` 的 `git clean` | L6 |
| 仓库初始化 | 提交带前导斜杠的 `.gitignore` 条目；两条路径从编辑器搜索与系统索引中排除；接好产物重定向 | L5、L7、B2 |
| 创建时 | 准入检查，超限或超阈值直接拒绝 | T1、Q1、Q2、Q3 |
| 会话退出 | 清理已声明的 worktree，遗留项记入日志 | T5 |
| 移除 worktree | `git worktree remove` 并删除配套的缓存槽位 | T2 |
| 提交前 | `git status --porcelain` 不出现生成物路径；无被强制加入的缓存路径 | L5、B1、B1.1 |
| 定时扫描 | 只读报告：各仓库数量、存活时长、体积 | L1–L4、T2–T4 |
| 周期性 | 与上一周期对比前几名占用；清点缓存与模拟器 | B5、C1–C3 |

定时扫描只报告，不删除。删除始终是显式、经确认的动作，且每个路径都要附上可核实的理由。

## 7. 例外

**X1 — 例外必须写明规则、路径与失效日期。**

例外只有在被写下来时才成立：豁免的规则、路径、理由、以及失效日期。统一记录在仓库根目录
的一个文件里——`.worktree-keep`，每行一条，这样同一个文件既是豁免凭证，也是该路径
为何仍在的说明。

每行以制表符分隔，因为路径本身可能含空格：

```
<路径>	<规则[,规则…] | *>	<YYYY-MM-DD>	# 该路径为何保留
```

四个字段都是必需的。`*` 表示该路径豁免全部规则；列出具体规则时只豁免列出的那些，
因此对 B1 的豁免不会顺带放过 T4。日期是豁免停止生效的那一天——从那天起，该路径与其他
路径一样被报告。

没有失效日期的「例外」不是例外，而是旧习惯换了个说法。同一条规则若因同一原因被豁免两次，
说明规则本身有误或定义不清——应当修正规则，而不是加第三个例外。

## 8. 本规范如何被检查

Worktree Cleaner 每次审计一个仓库，对上表中的规则逐条给出结论：符合、建议处理、违规，
或**未检查**。它只读：只报告，从不删除，而且报告不会改变任何一项「是否可删」的判断。

| 规则 | 审计读取的依据 |
|---|---|
| L1、L3 | 已注册的 worktree 路径，对照 `<repo>/.worktree/`，以及彼此之间 |
| L4 | 每个 worktree 的目录名：slug、长度、日期后缀、仓库前缀 |
| L5 | 对两个声明路径执行 `git check-ignore -v`：是否存在、是否锚定、是否写在仓库自己的 `.gitignore` 里 |
| T1 | 已注册 worktree 的数量，达到上限 90% 时提前告警 |
| T2 | 分支已合入主线的 worktree |
| T3 | HEAD 提交时间与目录创建时间中较新的一个 |
| T4 | 目录的创建时间 |
| B1 | 每个被识别的产物目录，对照 `<repo>/build-cache/` |
| B1.1 | 扫描本身已取得的 Git 事实：是否被跟踪、是否被忽略 |
| B2 | `build-cache/` 下的槽位与已注册 worktree 的对应关系，以及 worktree 内是否出现第二个 `build-cache/` |
| B5 | 每个槽位的体积 |
| Q1、Q2 | 卷的可用空间与总容量 |
| X1 | `.worktree-keep`，逐字段检查 |

以下规则会被报告为**未检查**而不是「符合」：L2（第二个 clone 在扫描路径之外）、
L6（已经执行过的命令）、L7（编辑器与系统索引配置）、T5（会话退出）、B3 与 B4（构建
如何使用缓存）、Q3（准入发生在创建时）、以及 C1–C3（机器级，超出一个仓库的范围）。
扫描看不见的规则会如实说明；沉默不等于合规。

「预防」的那一半在同一页上：每条规则都附带让它成立所需的接线——两条忽略条目、
缓存槽位变量、拒绝 `git clean -x` / `-X` 的 shell 包装器，以及关闭 worktree 并删除
配套槽位的两条命令——因此可以在创建第一个 worktree 之前就照着做完，而不是等磁盘满了再回头。
